# SOURCING — blocksworld

Phase 1 (sourcing only, per SPEC.md AMENDMENT). No task.py / generator code written.

## Target task (recap)

Blocks World state tracking: prompt gives a start state and a sequence of
pick-up/put-down/stack/unstack actions; scratchpad shows the stacks after each
action; answer is the final state. Knobs: blocks, depth.

## Candidates found and vendored

### 1. `vendor/LLMs-Planning/` — karthikv792/LLMs-Planning (aka PlanBench)
- URL: https://github.com/karthikv792/LLMs-Planning
- Commit: see `vendor/LLMs-Planning.commit` (cloned shallow, `.git` stripped after
  recording the hash to save space)
- License: MIT (LICENSE file present, copyright Valmeekam Karthik 2024)
- Citation: Valmeekam, Marquez, Olmo, Sreedharan, Kambhampati, "PlanBench: An
  Extensible Benchmark for Evaluating Large Language Models on Planning and
  Reasoning about Change," NeurIPS 2023 Datasets & Benchmarks Track
  (arXiv:2206.10498). Also houses data for the earlier "On the Planning
  Abilities of Large Language Models" (arXiv:2302.06706).
- Contents kept (pruned to blocksworld only; mystery-blocksworld and other
  PlanBench domains dropped to save space; raw `responses/` transcripts
  dropped, `.git` history and `planner_tools/` solver binaries dropped):
  - `plan-bench/pddlgenerators/blocksworld/domain.pddl` — canonical 4-operation
    PDDL domain (pickup/putdown/stack/unstack with clear/on-table/arm-empty/on
    predicates) — directly usable as the ground-truth action-legality spec.
  - `plan-bench/prompts/blocksworld/task_7_plan_execution.json` — **this is
    exactly our tracking formulation**: 500 instances, each giving a start
    state in natural language + an `[ACTION SEQUENCE]` of 1-3 actions, asking
    for the `[RESULTING STATE]`. It's single-shot (one resulting state after
    the whole sequence, not one state per action), and only 1-3 actions deep,
    but the state predicates, action vocabulary, and prompt scaffolding are a
    ready-made template to extend to per-step tracking at arbitrary depth.
    Ships a `ground_truth_plan` field (a symbolic state, e.g.
    `["holding_d","on_a_b",...]`) as the reference answer.
  - `plan-bench/instances/blocksworld/` — PDDL problem instances (start+goal
    states) generated by the IPC blocksworld generator, at multiple sizes.
  - `plan-bench/results/blocksworld/` — accuracy results for the PlanBench
    paper's own tasks (plan generation, plan verification, plan execution,
    etc.) by model.
  - `llm_planning_analysis/` — the sibling "On the Planning Abilities of
    LLMs" codebase (pddlgenerators, instances, results, results_backprompting)
    for blocksworld, pruned the same way.
- Assessment vs. common interface: has a real PDDL-verified action simulator
  design and a directly-relevant `plan_execution` prompt family, but no
  `Instance`/`generate`/`solve`/`check` shape, no seeded procedural generator
  usable off the shelf (their generator is a Fast-Downward-era PDDL problem
  generator, not a pure-Python stdlib seeded RNG generator), and the tracking
  granularity (whole-sequence result, not per-action state) doesn't match
  SPEC.md's one-state-per-step requirement. Missing: per-step state emission,
  Instance dataclass wrapper, differential solve()/check(), rigid single-line
  step format with atomic tokens.

### 2. `vendor/cot-planning/` — karthikv792/cot-planning
- URL: https://github.com/karthikv792/cot-planning (linked directly from the
  Stechly/Valmeekam/Kambhampati "Chain of Thoughtlessness?" paper, footnote 1,
  as "Resources and source code for planning experiments")
- Commit: see `vendor/cot-planning.commit` (`.git` stripped after recording)
- License: **none found** — no LICENSE file in the repo. Treat as
  all-rights-reserved; code/data read here for reference and reimplementation
  only, not for verbatim redistribution.
- Citation: Stechly, Valmeekam, Kambhampati, "Chain of Thoughtlessness? An
  Analysis of CoT in Planning," NeurIPS 2024 (arXiv:2405.04776).
- Contents kept (pruned: raw per-instance LLM response blobs trimmed where
  huge; kept `results/blocksworld_state_tracking/*` in full since those are
  small structured JSON with per-instance correctness labels):
  - `configs/blocksworld_state_tracking.yaml` +
    `instances/blocksworld_state_tracking/` +
    `example_query_prompts/blocksworld_state_tracking/upb.txt` — **this is a
    near-exact match for our target formulation.** The `upb.txt` (Universal
    Blocksworld algorithm prompt) example shows a per-action scratchpad with
    explicit `Current State: ... / Action: ... / Reason: ... / Resulting
    State: ...` for every step in the plan, numbered 1., 2., 3., ... — i.e.
    already one full state per step, step-indexed. It's a *planning* prompt
    (the model produces the actions itself) rather than a pure *tracking*
    prompt (actions given, only track state), and the per-step block is
    verbose prose (4 lines/step) rather than SPEC.md's required single rigid
    line per step — but the state representation, action vocabulary and
    per-step granularity are exactly what we need, and it would take only
    the actions from the ground-truth plan and drop the "Reason" line to make
    it a tracking prompt.
  - `results/blocksworld_state_tracking/{gpt-4-turbo-2024-04-09_chat,
    claude-3-opus,gpt-4_chat}/*.json` — **real published-style per-instance
    results on 270 instances**, each row has `llm_raw_response`,
    `extracted_llm_plan`, `llm_correct`, `llm_validity`, `Number of blocks`.
    Computed directly from the vendored files (not the paper text):
    - claude-3-opus, CoT (upb) prompt: 3/270 correct = 1.1%
    - claude-3-opus, no-CoT (po) prompt: 31/270 correct = 11.5%
    - gpt-4-turbo-2024-04-09, CoT (upb) prompt: 9/270 = 3.3%
    - gpt-4_chat, CoT (upb) prompt: 12/270 = 4.4%
    - gpt-4_chat, no-CoT (po) prompt: 20/270 = 7.4%
    These numbers are for the *planning* variant of state_tracking (model
    generates the plan) at this domain's default block-count distribution,
    not a pure given-actions tracking task, but they're a genuine, low-noise
    reference point for "how hard is state bookkeeping over blocksworld
    stacks" and go straight into desk.json `published_data`.
  - `instances/blocksworld_state_tracking/domain.pddl` — same 4-op PDDL
    domain as candidate 1 (pickup/putdown/stack/unstack), confirms action
    semantics are standard across both repos.
  - `Executor/` — a from-repo PDDL plan executor/validator (thin wrapper,
    not fully self-contained without their other utils) — useful as a
    cross-check reference when writing our own from-scratch simulator, not
    directly pluggable.
- Assessment vs. common interface: closest match found for the exact
  domain+granularity we want, but still no seeded pure-stdlib generator, no
  Instance dataclass, verbose multi-line-per-step format needs compression to
  SPEC's rigid single-line template, and it's a planning (produce-the-actions)
  prompt not a given-actions tracking prompt (our assignment is specifically
  tracking). No license, so treat as inspiration/spec source, not code to
  paste in verbatim.

## Also found, not vendored
- `github.com/kstechly/cot-scheduling` — sibling repo from the same paper's
  footnote, but for the *scheduling* domain (not blocksworld) — out of scope.
- BIG-Bench-Hard's `tracking_shuffled_objects_*` tasks are a *different* type
  of object-tracking task (shuffled physical objects, not stackable blocks)
  and are already the subject of the sibling `cup_shuffling` task directory
  in this library — not re-vendored here to avoid duplication.
- IPC (International Planning Competition) blocksworld generators are the
  ultimate upstream source of the PDDL problem generators both repos above
  already vendor a copy of (`pddlgenerators/blocksworld/`); no need to fetch
  separately.

## Recommendation

**Usable with a thin wrapper**, leaning toward "must write" for the core
generator, but strongly informed by candidate 2. Concretely for the build
phase:
- Action legality rules, predicate vocabulary, and state-string phrasing:
  reuse the PDDL domain (`clear`/`on-table`/`arm-empty`/`on`, 4 actions) from
  both repos — this is genuinely standard PlanBench Blocksworld, no need to
  invent new semantics.
- Per-step scratchpad shape: adapt cot-planning's `upb.txt` example (strip the
  "Reason" line, compress "Current State: ... Resulting State: ..." down to
  SPEC.md's required single rigid line, e.g.
  `step 4: unstack C B -> table:[D] towers:[A-B,C]`), converted from a
  planning prompt to a given-actions tracking prompt as assigned.
  This is not a copy-paste — a fresh, seeded, pure-Python generator + two
  independent state-transition implementations (generate-side simulator +
  solve()-side differential-check simulator) still need to be written from
  scratch, since neither vendored repo ships a stdlib-only seeded generator
  or an Instance-shaped output.
- Use PlanBench's `plan_execution` task (candidate 1) as a secondary format
  reference for how they phrase "resulting state" answers.
- desk.json `published_data` should cite both the PlanBench paper
  (arXiv:2206.10498) and Chain-of-Thoughtlessness (arXiv:2405.04776), the
  latter with the real per-instance accuracy numbers computed above.
