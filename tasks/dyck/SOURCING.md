# SOURCING — dyck

Phase 1 (sourcing-only, per SPEC.md AMENDMENT). No task.py / generator code written.

## Candidates vendored

### 1. `vendor/BIG-Bench-Hard` (shared symlink to `../grid_navigation/vendor/BIG-Bench-Hard`)
- Source: github.com/suzgunmirac/BIG-Bench-Hard, commit `9ee07bd481feebf959a6b59d61ea57bdcf30964d` (2022-10-22), MIT license.
- Paper: Suzgun et al. 2022, "Challenging BIG-Bench Tasks and Whether Chain-of-Thought Can Solve Them," arXiv:2210.09261.
- Contains `bbh/dyck_languages.json` (canary-tagged fixed examples: input = a Dyck-k prefix, target = the correct closing sequence) and `cot-prompts/dyck_languages.txt` — a 3-shot CoT prompt whose scratchpad already matches the assignment's target format almost exactly: one numbered line per input symbol, each showing "stack: <current stack contents>", ending with "the final stack is X" and the derived closing sequence. This is the single best format reference found across all candidates.
- Also has raw Codex (code-davinci-002) outputs + eval metrics — used below for exact published numbers, computed from the vendored `eval_metrics.jsonl` directly (not transcribed from the paper's PDF table).
- Assessment: fixed dataset only (no generator, no reference solver, no k/length/depth knobs). Scratchpad style is directly reusable as a template reference, but the data itself cannot be extended past its ~250 fixed canary-tagged examples.

### 2. `vendor/BIG-bench-google` (sparse checkout of google/BIG-bench)
- Source: github.com/google/BIG-bench, path `bigbench/benchmark_tasks/dyck_languages/`, commit `092b196c1f8f14a54bbc62f24759d43bde46dd3b` (2024-01-18), Apache 2.0 license.
- Contains only `task.json` (1000 fixed Dyck-4 examples, lengths bounded [4,100]) and `README.md`. The README states the task "was initially created as a Python programmatic task... but was later converted to JSON format to simplify post-analysis and support batching," and that the *old* programmatic version lived in a `/legacy` folder — that legacy folder does **not** exist in the current `main` branch at this commit (checked directly, not present), so the original generator script referenced by the README could not be recovered from this repo as it stands today. Data was produced via a "probabilistic context-free grammar (PCFG)" per BIG-bench's own docs, but that PCFG code is not shipped in the currently-checked-out tree.
- Assessment: fixed dataset only, same limitation as candidate 1 but with 4x more examples and only Dyck-4 (no k-knob exposed in the data itself, though presumably the vanished legacy generator had one).

### 3. `vendor/dyck-transformer` (full shallow clone, github.com/princeton-nlp/dyck-transformer)
- Source: github.com/princeton-nlp/dyck-transformer, commit `5d21fcfff22a2f1446e9a62d80ca3ee08ff0e419` (2021-05-31).
- Paper: **Yao, Peng, Papadimitriou, Narasimhan, "Self-Attention Networks Can Process Bounded Hierarchical Languages," ACL 2021, arXiv:2105.11115** — this is exactly the paper the assignment asked to cite for theory, and its official code release.
- **No LICENSE file found in the repository root** — treat as all-rights-reserved for code reuse purposes until/unless a license is confirmed elsewhere (e.g. a license badge on the GitHub repo page not visible from the cloned tree); citation of the paper is unaffected regardless.
- Contains `src/generate_mbounded_dyck.py`: a genuine, well-structured Dyck-(k,m) generator (`DyckPDFA` class) implementing a probabilistic finite automaton over a stack-based state machine. Directly exposes exactly the knobs the assignment wants:
  - `bracket_types` = k (number of bracket types)
  - `max_stack_depth` = m (max depth knob)
  - `length_min`/`length_max` (length knob)
  It internally tracks `state_vec` (the stack) at every step via `update_state()`, i.e. it already computes the per-step state the assignment's scratchpad needs to render — this is the closest thing to a ready reference implementation of the *state-tracking logic* found across all three tasks I sourced.
  - Caveats: (a) uses `torch.distributions.Categorical` for sampling and `torch.manual_seed` for reproducibility — SPEC.md requires pure stdlib, so the sampling logic (trivial: uniform choice among legal next-bracket actions) will need reimplementing with `random`, not reused as-is; (a hardcoded seed comment in the file also warns "random seed is hardcoded to ensure reproducible data," consistent with SPEC's own determinism requirement, a good sign the underlying algorithm is seed-stable in spirit even though the code must be ported off torch); (b) it generates *complete* well-formed Dyck strings, not "prefix + required closing suffix" pairs — the assignment needs a Dyck-k *prefix* (not a complete balanced string) whose stack is non-empty at the cut point, so the generator would need to be run and then truncated at a random position, with the true suffix taken as the correct closing sequence (this truncation logic is not in the repo and must be written); (c) no scratchpad/CoT emitter and no reference solver-as-a-function (only bulk dataset-writing to disk) — solving a truncated prefix (closing sequence = the current stack contents' matching brackets, reversed) is a straightforward function to write independently, but is not present in this repo as a standalone `solve()`.
- Also present but not directly relevant: `src/run_lm.py`, `acl2021/` (yaml experiment configs for their transformer/LSTM experiments), `data/` (their own pre-generated Dyck-(k,m) corpora at various k/m settings — could in principle be read directly, but these are fixed samples like BBH, not a source of *fresh* seeded instances, so they don't satisfy the assignment's non-contamination goal any better than BBH itself).

## Recommendation

**Usable with a thin wrapper.** Of everything found across all three of my assigned tasks, `dyck-transformer`'s `DyckPDFA`/`generate_mbounded_dyck.py` (candidate 3) is the strongest generator match: it already parametrizes exactly the assignment's three knobs (length, k, max depth) and already computes the per-step stack state needed for the scratchpad. It needs: (1) porting off `torch` to stdlib `random` (the sampling logic itself is simple — uniform choice among currently-legal push/pop actions — so this is a small, mechanical rewrite, not a redesign); (2) a truncation step to turn a complete Dyck string into a "prefix + required closing suffix" instance, which is not in the repo; (3) a rigid one-line-per-symbol scratchpad emitter, best modeled on the already-vendored BBH `cot-prompts/dyck_languages.txt` format (candidate 1), which is closer to the assignment's target style than anything in the Yao et al. repo; (4) an independently-written `solve()` per SPEC's differential-check requirement (trivial for Dyck: solve by literally running a stack and reversing/closing it, must not reuse `DyckPDFA.update_state` verbatim to keep solve() and generate() independent as SPEC requires). None of the three candidates ships a working `task.py`-shaped wrapper matching the common interface; all require code in a later phase.
