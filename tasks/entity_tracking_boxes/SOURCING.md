# SOURCING — entity_tracking_boxes (Kim & Schuster 2023)

Phase 1 sourcing only, per SPEC.md AMENDMENT. No task.py / generator written yet.

## Candidate vendored

### `vendor/entity-tracking-lms/` — sebschu/entity-tracking-lms (official repo)
- Source: https://github.com/sebschu/entity-tracking-lms, commit `8400de051ef4ad9483cc37dee3017b37a48dafd7`.
- **License**: no LICENSE file in the repo. Treat as all-rights-reserved / academic-courtesy use only; cite the paper (see below) if the generator or data are used. Flagged as a caveat in `desk.json`.
- Contents vendored (full repo, `.git` stripped):
  - `src/dataset_generation/generate_boxes_data.py` (1017 lines) — **a real, working procedural generator.** Builds a `WorldState` (N boxes, each holding 0..max objects from a 100-word BNC-frequency object vocabulary), samples an initial state via Poisson-distributed occupancy, then samples a sequence of `move` / `remove` / `put` operations, rendering both the operations and box-content descriptions as natural-language sentences via string templates (`_OPERATIONS_DICT`). Supports knobs: `--num_boxes`, `--num_operations`, `--expected_num_items_per_box`, `--max_items_per_box`, `--seed`, plus dataset-construction options (disjoint vocab, alt-forms, ambiguous-reference, "move contents" variant, pragmatic modifier-dropping).
  - `data/boxes-dataset-v1.zip` — the paper's actual dataset, **password-protected** (`iamnotaLM`, stated in repo README) specifically to avoid training-data contamination. Confirmed extractable with that password; sampled a record: format is T5-style masked cloze (`"sentence_masked": "...Box 0 <extra_id_0> .", "masked_content": "<extra_id_0> contains the bill"`), i.e. **not a scratchpad/CoT format** — it's a single-shot cloze query per (scenario, box, operation-count) tuple, no intermediate per-op reasoning trace in the data itself.
  - `data/objects_with_bnc_frequency.csv`, `data/objects_not_in_bnc.csv` — the object-name vocabulary (BNC-frequency filtered, as described in the paper), directly reusable.
  - `model-outputs/model-outputs.zip` — password-protected model prediction logs, not needed for our purposes.
  - `src/evaluation/compute_metrics.py` — reference **accuracy scorer** (not a solver — it grades model output against gold `masked_content`, doesn't independently derive gold from scratch), tolerant to object-order/determiner variation. Useful as a template for `check()`'s tolerant parsing.
  - `scripts/data_generation/*.sh` — exact CLI invocations used to produce each of the paper's splits (base, NumOps, Vocab, AltForms, AmbiRef, MoveContents) — useful for knob-value reference.
- **What it contains vs common interface**:
  - Generator: yes, real, but **requires `numpy`** (`from numpy.random import poisson`) — SPEC requires pure stdlib. Easy to strip (replace Poisson sampling with `random.randint`/`random.choices`), so this is "thin wrapper" territory *only if* we're willing to reimplement the sampling in stdlib — otherwise it's a straight dependency violation.
  - No rigid one-line-per-op scratchpad: the dataset is a direct-answer cloze task (query one box's final contents), not a CoT trace showing full state after each op. SPEC requires `Instance.steps`/`states` with one line per op showing the *full* state (all boxes), which this generator does not produce (it only prints the *box-being-queried's* running content changes, and only for scoring/analysis purposes via `numops`/`numops_by_op` counters — not as rendered text).
  - No independent `solve()` — the WorldState class *is* the ground truth simulator (each op mutates `self.boxes` directly), so an independent solver would need to be written separately from the generator's own state machine to satisfy SPEC's differential-check requirement anyway.
  - Answer format (`masked_content`) is a set of object names in a box, not a single short exact-match string in the general case (a box can hold up to `max_items_per_box` objects) — need a canonical serialization (e.g. sorted comma-joined list, or restrict `max_items_per_box=1` for a single-token answer) to satisfy SPEC's "answer is a single short string."

### Considered but not found
- Exhaustive GitHub/web search for other implementations of this exact "boxes" entity-tracking task (Kim & Schuster 2023) turned up nothing beyond the official repo — no HuggingFace dataset mirror, no lm-evaluation-harness task, no third-party reimplementation. This appears to be an under-adopted benchmark relative to BBH; the password-protected zip (specifically designed to block scraping/mirroring) likely explains the lack of HF/harness mirrors.
- A related but distinct task, "Alchemy" (Long et al. 2016, beaker/liquid state tracking) and its reanalysis by Li et al. 2021 (probing classifier on T5/BART entity-state decoding), is discussed at length in the Kim & Schuster paper itself as prior work they found methodologically insufficient (Section 2 "Reanalysis of Li et al. 2021" — 62.7% of probed states are unchanged-from-initial, so a trivial baseline nearly matches reported accuracy). Not vendored: it's a different task (Alchemy, not boxes) and the paper's own critique argues against using it as a template.

## Reference: `vendor/paper/kim_schuster_2023.pdf`
Kim & Schuster, ACL 2023, "Entity Tracking in Language Models" (aclanthology.org/2023.acl-long.213, arXiv:2305.02363). Read in full (pp. 1-9) for task design and results. Key facts pulled into `desk.json`:
- Task: N=7 boxes, m=3 max objects/box, e=2 expected objects/box initially, |O|=100 object vocabulary (BNC-frequency filtered), NumOps fixed to 12 in the main dataset, evaluated after every op (91 test examples per scenario = 7 boxes × 13 states-including-initial).
- **This paper evaluates in-context few-shot / finetuned accuracy, NOT chain-of-thought.** There is no CoT variant in this work — models are prompted directly for the final box contents (a cloze completion), so there are no "published CoT vs no-CoT numbers" for this task from the source paper (unlike BBH). Only GPT-3.5 `text-davinci-003` (code+RLHF-trained) shows non-trivial entity tracking (>25% fully-correct after 7 operations vs near-zero for GPT-3 `davinci` and Flan-T5, which just repeat the initial state); see Table 1 and Figures 2/5. Finetuned T5-base reaches near-perfect accuracy in-distribution and >45% on longer held-out operation sequences (Section 5, Figure 6).

## Recommendation

**Usable with a thin wrapper for the underlying simulation logic, but the CoT/scratchpad rendering must be written fresh.** Concretely, for the next phase:
- Reuse: `WorldState` state-machine logic (port off numpy to stdlib `random`), the object vocabulary CSVs, and the natural-language operation templates (`_OPERATIONS_DICT`) — these are directly aligned with SPEC's task description ("N boxes holding objects, operations move/remove/put").
- Must write fresh: the rigid one-line-per-op scratchpad renderer (full all-boxes state after each op, not just the queried box), an independent `solve()` (re-simulate from the op list without reusing `WorldState`, e.g. a plain list-of-sets replay), `step_spans()`, and a stdlib-only Poisson-ish initial-occupancy sampler (`random.choices` over a small weighted range is sufficient — doesn't need true numpy Poisson).
- Cannot use the vendored dataset directly at all: it's password-protected specifically against redistribution/contamination, and its format (single-box cloze, no full-state trace) doesn't match `Instance.steps`/`states` anyway. It's useful only as ground truth for validating our fresh generator's *distributional* choices (vocab, N=7/m=3/e=2 defaults) against the published paper.
